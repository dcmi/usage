### BIBO 2.0 (Niklas, Tom)

BIBO 2.0 proposal: https://github.com/dcmi/bibo/issues/8

Tom: Keep using numbering system and call it 2.0? to signal that it is modernized and without the Protégé baggage and rebranded as a vocabulary (?); and then plus new things for the additions

Niklas: versioning -- may lead to questions about differences between BIBO and DCTERMS but I like release process numbers; am also in favour to bumping number to 2.1 for SRAP-related additions; we could also have internal patch numbers for fixing typos etc.; signal also to users that they need to be aware of changes. In favor of using "semantic versioning".
[shares screen]

[shows BIBO 2.0 proposal in Github from Feb] We could split out the "document status" and "degrees" into separate documents. Process-wise looks simple and clean to maintain. We had a call about this. 

Re: naming, have not done anything yet.

Want to define release routine. Main work to prepare by ensuring we can generate RDF/XML, TTL, NT. will discuss with Nishad. Take inspiration from OpenWEMI - so everything bundled in one repo - Turtle file and generated docs updated in place. So internal redirects could change following pattern of OpenWEMI.

Currently, URL resolves to HTML. "ontospy" tool. Work I have done is in one PR. Haven't discussed latest one yet with Tom. Generate serializations and HTML. Commits are done so can follow in sequence. [Shows anatomy of changes:]

- Moved status and degree into separate files.

Addition appears to have been due to Protege. 

Other commits here are about plumbing for generating from Make file for serializations. Ensure they are reproducible. Separate tool that uses Oxigraph. Want something predictable and reproducible.

As Tom and I discussed, putting generated files under version control. Some details that are out of scope for SRAP per se. Update everything from Make file - patterns for everything - details discuss with Nishad... PURL redirects. Would love to make improvements. Should we do better in BIBO with documentation - eg, with examples? Point is to make it simple. Splitting out of status and degree terms - makes sense to have separate pages. Page for just three terms? But it does follow a pattern. Would not oppose folding them into main document if we decide. And it is dark-mode adaptable.

Tom: You are welcome to look into the details yourselves but we will do our best to draw your attention to the things that need to be decided.

Karen: Basic questions. Will BIBO 2.0 continue to be a rather strict OWL vocabulary?

Niklas: We would not redefine anything.

Karen: So this means reorganizing what is there and adding a few properties.

Niklas: We looked at OWL restrictions, coupled with classes. But the restrictions are mostly about cardinality. Qst whether we should remove them. A way to do application-profile-like things. Was this intentional or the result of flipping a switch in Protege?

Karen: 

Niklas: BIBO uses dc:title for its title - things like that are kept. Scholarly resources would be subprop. When you get RDF data from BIBO namespace you will not have assertions about terms in other namespaces (except with respect to BIBO terms). 

Phil: What Niklas said... BIBO does do double duty as vocabulary abnd application profile. Suggestions what can be done. Agree we don't need axioms about DC terms. Could have an AP. Could put in just the terms: DC rdf:type Class - deals with confusion for people who expect to see all terms needed.

Karen: I like that. Removing them leaves people at sea. Even as separate section. Shapes would need title, creator. Really prefer being logically complete rather than technologically strict.

You could write your own but should look like what others encounter. Can look at OpenWEMI page - based on Silvio Peroni's and pylode by Rob (PROF) - recommend using or imitating.

Karen: Should be packaged in way that can be shared.

Niklas: Looked from POV of restrictions. Examples from previous BIBO example page. Starter for doing something. Other ways to point, rdfs:seeAlso - very simple. Have not seen such inclusions in SKOS, FOAF - would not mix up ontology in RDF could include reference to SHACL profiles if needed.

Phil: Might help with inter'y to maintain level of expectation of current BIBO because if only BIBO namespace document says nothing about expecting to use with DC terms.

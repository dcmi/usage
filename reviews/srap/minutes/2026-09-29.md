### DCTERMS Accessibility Properties

Proposed text for public comment
- https://github.com/dcmi/dc-srap/issues/103#issuecomment-4878025815

Discussion if and how to move this forward

Tom: our concern is whether solving this is critical for publishing SRAP; we like the proposals and think they are a good idea but if we where to approve a property that takes URIs we need to recognize that this would be an emerging pattern that includes in-house vocabularies such as the ones by the National Library of Sweden; one way would be to approve properties in BIBO now and declare intention to also put them into DC Terms later, or we really try to get a coordinated effort of National Libraries of Sweden, Finland, and Stanford going to test this (URI-based) approach out but should we really put SRAP on hold for this or can we approve SRAP without accessibility for now?

Kalli: could we approve the accessibility summary with free text and move on with SRAP and postpone URI-based property to after SRAP publication, as a compromise?

Karen: dilemma seems to be URI-based accessibility vs. accessibility from standard list of terms vs. somebody just typing in something?

Niklas: URIs and standard list are the same, we should not encourage list without URIs

Osma: same opinion -- lists should have URIs, problem isthat real world does not agree, they have lists w/o URIs and that will not be solved by them unless we fix it ourselves somehow: personally I do not mind a delay for SRAP publication; SRAP was just a vehicle to get this information into DC Terms (and nowadays  also BIBO)

Niklas: KB wants to take an active part in this but of course it would be a coordination effort between institutions and DCMI; "accessibility facet" is good expression since we also aim for these structured values for simpler navigation in catalogues (which is actually required by Swedish law)

Tom (wants to clarify his own position with himself): W3C community came up with six or seven properties and each constitutes a separate list of values; if we approve a URI-based property we would take a different approach, you can take concepts of different facets; there are no URI-based vocabularies to be used that way out of the gate, would require some work

Karen: we have not found any URI-based vocabularies for this? Tom: correct.
Karen: Osma, are you saying that we can finalize SRAP without accessibility?

Osma: no, I would prefer holding up SRAP and trying to solve the accessibility issue, SRAP was not a purpose in itself but a push for useful changes in DC Terms and BIBO and demonstrate how we can reflect scholarly resources in those vocabularies, and this seems a very useful change

Tom: that is a good way to see SRAP; there are not URI-based vocabularies except internally (but publicly) at National Library of Sweden; havig some kind of coordinated testbed between institutions would be a good thing

Niklas: I agree, National Library of Sweden does not want to be the sole authority for these terms, rather a coordinated effort as wide as possible would be desirable, and having these terms in DC Terms (or BIBO) would be great

Karen: In the library world we have a long history of having lists and then saying where the list came from, so the lists themselves had IDs; that might suffice and individual terms would not have to have IDs/URIs? could we do something similar within our shapes?

Tom: that was the purpose of the Vocabulary Encoding Schemes in DCMI in order to support literal values from authority lists; we had a discussion how this fits with RDF and declared these to be data types bc the abstraction of a data tpe in RDF is literal values that map to (putative) concepts, it is not the way RDF data types are generally used now, it has not caught on, but nobody has convined me that this would not still work; I am not saying it is a good idea but also it would not be wrong, technically

Osma (put an example in the chat):
:mydoc dct:accessibility "ARIA"^^dct:accessibilityFeature .

Niklas: technically it could work (...); it is a bit more accessible than plain strings bc you can reference the data type and discover what the actual term does mean, a more idealistic view, and libraries are using these things for cooperations, so it is not just an academic view

Tom: I would also prefer URIs; we were never quite sure what would be the best way of referencing data types, what is the standard practice?

Osma: If there is a way to ask the W3C to fix this by making a URI vocabulary that would be ideal but would take some time

Tom: one of the issues of Vocabulary Encoding Schemes (VESs), we had a proposal in 2004 to make it easy to create new VESs in DC Terms but then that creates the burden to maintain the link between those and an external vocabulary; some possible scalability / technical dangers, we would need to create a registry, honor versioning changes, etc. etc.

Niklas: RDF interpretations may "recognize" datatypes outside of RDF and XSD, but are not required to (and if so, it's more tricky formally to define the _value space_, etc. (than to look up a concept URI)).
